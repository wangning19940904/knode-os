## 1. 语料：分层，不是删除（原因 ①）

**不建议直接过滤掉小语料。** 两个理由：真实的个人知识库大多就是这个规模，产品在这个规模上的诚实卖点需要有数字；小包还承担对照和回归的作用。

按"一个 agent 靠 shell 能不能读完"分三层，每层问不同的问题：

| 层 | 规模 | 包 | 问什么 | 跑什么 |
| --- | --- | --- | --- | --- |
| T0 | 能放进上下文（约 120 万字符以内） | finance、law、medicine、literature、email、life、reports 1× 等 19 个 | Ask 相对普通 RAG 的质量和成本；更新、涌现类题 | 只跑单次调用和更新套件，不进 agent 对比的主结论 |
| T1 | 超出上下文、grep 仍能应付 | reports x10、loong-finance、mudabench | 页面和工具能否省步骤、省 token | 阶梯臂，主指标是成本 |
| T2 | grep 可能退化 | reports x100、wiki-hops、crud-news | grep 在哪里开始吃力，知识库在那里是否多答对 | 先只跑 grep 和 rag 两臂（规模门槛），退化了再构建 |

规模门槛的判读：同一批题从 10× 到 100×，grep 正确率掉 0.05 以上，或每个正确答案的 token 升到 1.5 倍以上，或 10% 以上的会话撞到命令上限 → 在该包上构建。都没有 → 这类语料在这个规模不需要知识库，换语料类型。

## 2. 题目：按题族定数量，并且先冻结（原因 ②）

**数量。** 关键不是每包 30 题还是 100 题，而是每个题族有多少题。设计 33 D4 定的是每族至少 60 题，但上一轮按题型轮转，每个题型只有 3 题。样本量按"有分歧的题数"算：C 道有分歧的题里，一臂要赢其中 (1 + 2.8/√C)/2 才显著。C = 40 时要赢 72%，C = 100 时要赢 64%。所以：

- 有余量的题族（汇总、时间线、多跳、当前状态）每族 60–100 题。
- 对照题族（精确查找、改写、跨语言）每族 20 题就够，它们的作用是发现 harness 故障。
- 运行前用 `--agent-sample-only` 打印预期分歧数，少于一半不跑。

**难度。** 同意减少直接 grep 能命中的题，但要防一件事：**不能照着知识库会编译什么来出题**，那样测出来的优势没有意义。规则：

- 题族按用户需求定义（跨文档汇总、截至某日的状态、别名、无共同词的链），不按产品功能定义。
- 题目和 gold 在生成环节改动之前冻结；改生成之后只在冻结的题上测，另留一批从未见过的题做最终确认。
- 用已有的 `eval pack grepability` 和 `measure.json` 的 `literalTerm` 控制可直接命中的比例，对照题除外。
- gold 来自脚本或数据集作者，不来自被测系统的输出。

**用哪些题。** `synthetic-reports-zh-v3` 系列已经有按这个思路做的题族（hop 117、aggregate 93、timeline 70、current-state 66），只是没被充分使用。真实语料用 `real-wiki-hops`（FanOutQA + FRAMES，题目不点名文档）。

## 3. 生成：让答案进知识库（原因 ④，以及"提前固化财报指标"）

### 3.1 现状

`real-loong-finance` 这次构建（574 篇）：

- 117 道单文档数字题的标准数字：原文里有 115 道；该文档的摘要页里 33 道（28%）；该文档的 claims 里 28 道（24%）。
- 每篇文档的 claims 中位数是 50。228 篇文档正好落在 45–50 条，这些文档的中位长度是 1.4 万字符，即两个分段。原因是抽取提示词限定每次调用最多 25 条 claim（`EXTRACT_CAPS.claims`，`src/graph/llm-extract.ts:33`），而一张资产负债表就有上百行。
- 摘要页的 Figures 段上限 20 行，claims 区上限 30 条（`src/wiki/summary.ts`、`src/wiki/pages.ts`）。没有任何规则要求保留报表行项目。
- 没有表格到数据集的抽取，`datasets` 只来自外部数据源同步。
- 构建时没有任何跨文档的模型综合。Synthesize 阶段已下线（设计 09），concept 页只能由研究任务或人来写，自动研究默认关闭。

结论：对财报这类以数字表为主体的文档，现在的知识库结构上装不下题目要的事实。这不是召回问题。

### 3.2 措施

1. **表格无损结构化（核心）。** 把报表行解析成类型化的事实行：文档、主体、期间、行项目原文、数值、单位与量级、原文行号。
   - `real-loong-finance` 抽查的 400 篇里 180 篇是 Markdown 管道表格，可以不调用模型直接解析。
   - 其余（英文 10-K、`real-mudabench`）是空格对齐的文本表，需要版面解析或一次专门的模型调用。这次调用按行输出，不受 25 条上限约束，只对数字密度高的分段触发。
   - 行项目名的归一化（"营业收入" = "revenue"）按**去重后的标签**做一次，不是每个数值做一次。这次构建有 12,717 个不同的 attribute 值。
   - 单位和量级必须是字段。上一轮 gold 的错误大多出在"人民币百万元""in thousands"上，被测系统会犯同样的错。
2. **摘要页指向表，而不是抄表。** Figures 段保留，另加"本文档的报表在哪几行"的锚点。页面的职责是导航和解释，数字由事实行承载。
3. **确定性的跨文档汇总页。** 从类型化事实直接渲染"指标 × 主体 × 期间"的对照表页，不调用模型，随事实变化重渲染（现有的依赖跟踪已支持）。这是 wiki 里第一种真正跨文档的页面。
4. **模型写的综合页仍然交给研究任务**（设计 15 的决定不变），但由查询驱动：哪些跨文档问题被反复问到，就建议为它写页（见 §4）。
5. **覆盖率作为门槛。** 新增一个不调用模型的命令：按题族统计标准答案出现在摘要页、实体或时间线页、汇总页、claims、类型化事实中的比例。数字类题族现在是 28% 和 24%，目标 0.8 以上；达不到就不跑 agent 评测。

### 3.3 防止为评测定制

结构化的对象是**所有**表格单元格，不是评测问到的那几个指标；派生指标（比率、增速）不预先计算，由查询时的计算路径完成。验收用冻结题加一批未见过的题。

## 4. 用中学习：把查过的东西留下来（新方向）

### 4.1 现状

产品里**没有**让第二次问更便宜的路径：没有答案缓存、没有保存的查询、Ask 或 agent 的答案不会自动成为页面。相近的机制都要人介入：

- `knode_commit` 和聊天里教的事实写成笔记，但进隔离区，要人提升。
- 问题页要显式排队一个研究任务。
- playbook 的修订要人接受。
- 热度只给检索排序加最多 5%。

评测里这些全部关闭（`track: false`）。

### 4.2 措施：三种写回，按风险从低到高

| 写回 | 内容 | 自动提升的条件 |
| --- | --- | --- |
| 派生事实 | 答案里核实过的数值，连同原文行号，写成一条类型化事实 | 引用的那一行在原文该行号处确实存在，且数值相符（确定性校验） |
| 取数方法 | "这类文档里这个指标在哪张表、用哪个口径"，写入 playbook | 同一方法在两篇以上文档上校验通过 |
| 问答页 | 问题、答案、引用，写入 `wiki/questions/` | 引用全部通过校验；被引文档变化时页面标脏（设计 37 第 3 阶段的引用依赖已有） |

校验不通过的仍进隔离区，和现在一样。

### 4.3 怎么评测

新增"学习"套件，一条按顺序提问的题目流：

1. **冷启动**：问一组题 S。
2. **热启动**，分四类重问：原题；改写；近迁移（同一指标换公司，或同一公司换指标）；远迁移（无关题，作对照）。
3. **更新**：加入一批改动了部分被引文档的新文档，再问一遍相关题。

指标：

- 热启动与冷启动的每题 token 比、正确率差。
- **污染率**：冷启动答错并被写回、热启动跟着错的比例。
- **过期率**：更新后仍给出旧答案的比例。
- 写回本身的成本，计入全周期成本。

**必须有的公平基线**：`agent-grep` 加一个它自己可以读写、跨题保留的笔记文件。没有这个基线，测到的是"有记忆对没记忆"，不是"知识库对笔记"。题目顺序跑两种，排除顺序效应。

## 5. 臂的设计：别让它只能更贵，也别让 knode 沦为 grep（原因 ③）

### 5.1 现状

- 提示词规定从 `wiki/index.md` 开始、回原文核对、引用原文路径。所以 protocol36 那轮 wiki 臂 100% 先读索引，0% 引用页面，每题命令数比 grep 多。
- 全臂（wiki + 原文 + 六个工具）只有 3–4% 的答案调用过工具。
- 纯工具臂 74% 的调用是 `knode_grep`。给 agent 的选工具指引本身就写着：查当前值、查精确数字，用 grep（`src/mcp/question-kinds.ts`）。原因写在同一处——后来的文档会用代号改值，抽出的 claims 可能漏掉。
- 没有任何工具能对多个点名的主体一次查出一张表。mudabench 的题要从 9–19 份年报各取一个数，一条 shell 命令能全读，一次 `knode_grep` 只返回有上限的一段，所以纯工具臂在预算 3 时 101/214 题被截停。
- `knode_ask` 在产品里存在，但两个 agent 臂都没有。

### 5.2 措施

1. **`knode_table` 工具**：输入指标、主体列表、期间，返回一张矩阵，每格带原文行号。依赖 §3 的类型化事实。这是 knode 能做而 shell 做起来贵的事：一次调用代替十几次读文件。
2. **入口按题型路由，不按索引。** 去掉"从 index.md 开始"，改成一张短的路由卡：跨主体的数字 → `knode_table`；历史和时间线 → `knode_claims order=timeline`；谁做了什么、链 → `knode_query`；换了说法的段落 → `knode_search`；其余 → shell。
3. **结构化结果带行号锚点**，核对只需要一条 `sed`。现在 agent 回原文重找一遍，是 wiki 臂更贵的直接原因。
4. **新臂**：
   - `agent-knode-wiki-first`：页面写明事实及来源时可直接作答并引用页面。
   - `agent-knode-delegate`：可以调用 `knode_ask`，模型开销计入该臂。这是产品的真实用法。
   - `agent-grep-catalog`：原文加一份不经模型生成的目录文件。mudabench 上 wiki 臂的 +0.078 里有 4 题只是帮忙找到了哈希命名的文件，这个对照把"目录"和"知识"分开。
5. **不靠拿掉 grep 来"避免沦为 grep"。** 拿掉只会让分数变差。标准改成遥测：结构化工具提供了证据的答案占比、每个工具调用后的正确率、相对 grep 省下的步数。工具被选是因为它更好用，才算数。

"结合 RAG 和图搜索"在全臂里已经有了（`knode_search`、`knode_graph_search`）。它们没被用，是因为在 grep 够用的题上它们不省事。所以要改的是工具能做什么（第 1、3 条）和题目（§2），不是再多给几个入口。

## 8. 成本和指标（原因 ⑦）

### 8.1 全周期成本

同意按"一次构建、长期使用"来算，但要把账算全：

> 总成本(N) = 构建 + 各次更新 + N × 每题成本；回本点 N* = 构建 ÷（grep 每题成本 − 知识库每题成本）

用现在的数字代入 `real-loong-finance`（构建 2.78 亿加权 token，574 篇，每篇约 48 万 token、28 次模型调用；grep 每题约 4.7 万）：

- 现在 wiki 臂每题比 grep 贵，**没有回本点**。
- 假设 wiki 优先臂把每题成本降 30%：约 2 万次查询回本。
- 假设全部走 Ask（每题约 1.9 万）：约 1 万次查询回本，但它在这个包上的正确率是 0.30 对 0.96。

所以"长期使用"要成立，两头都得动：每题要真的更便宜（§5），构建要便宜一个量级（§3 里不调用模型的表格解析是主要手段）。回本点应该成为每次运行都报告的数字。

报告要改的：

- 回本点按每个 knode agent 臂分别算，不只按 `knode-ask`。
- 更新批次和写回的成本计入总成本。
- 摊销点在 100、1,000 之外加 10,000，并画总成本随 N 的曲线。
- 构建成本同时报每篇文档的 token 和调用数。

### 8.2 指标表

大部分指标 harness 已经在记，缺的标"新"。

| 类别 | 指标 |
| --- | --- |
| 质量 | 正确率（按题族）；集合 F1；幻觉率；自信地答错；误拒答率；该拒答时拒答；过期答案率 |
| 依据 | 引用精确率和召回率（页面引用映射回原文，新） |
| 每题成本 | 加权 token；每个正确答案的 token；美元；延迟 p50 和 p90（p90 新）；工具调用数；撞上限比例 |
| 全周期 | 构建 token 每篇（新）；更新 token 每篇；回本点（按臂，新）；N = 100、1,000、10,000 时的总成本（10,000 新） |
| 稳定性 | 同一臂重复作答的不一致率；judge 复核不一致率；judge 对故意错答的放过率（新） |
| 覆盖 | 标准答案在页面、claims、类型化事实中的出现率（新） |
| 使用 | 结构化工具提供证据的答案占比（新）；每个工具调用后的正确率 |
| 学习 | 热/冷 token 比和正确率差；污染率；过期率（全新） |

主结论同时报两个数：正确率差，和每个正确答案的成本比。两者都带区间。

## 9. 路线

| 阶段 | 内容 | 模型开销 | 依赖 |
| --- | --- | --- | --- |
| P0 度量就位 | 覆盖率命令；全错题清单和盲审；Ask 的 prompt 重放脚本；wiki-hops 补判分；报告的回本点和指标改动（E2–E4、E6–E8） | 只有盲审和少量判分 | 无 |

## 10. 需要决定的事

1. **R5：链式题在 Ask 里做多轮检索，还是明确交给 agent 路径。** 前者每题多 1–2 次模型调用；后者承认 Ask 不处理这类题。
2. **用中学习的自动提升。** 是否接受"引用通过确定性校验就自动生效"，还是全部继续走人工接受。这决定学习套件测的是自动能力还是辅助能力。
3. **P5 的构建开销**是预先授权，还是等规模门槛结果出来再定。
4. **是否给单次调用加一个多轮分解 RAG 基线。** 外部评测里它能抹掉 wiki 对单轮 RAG 的大部分优势。
5. **§3 的表格结构化范围**：只做管道表格（不调用模型，覆盖约 45% 的 loong 文档），还是同时做文本对齐表（要模型调用或版面解析）。
6. 本文是否改写成英文并入其余设计记录。
